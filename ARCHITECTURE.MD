# Архитектура

| Модуль | Ответственность |

| ApplicationFiles | Пути комплектных файлов в lib относительно EXE |
| GameState / GameRules | Данные обоих режимов, правила начисления, маска, заставка и независимые копии состояния |

| QuestionBankReader / BankDocument / RoundRules | Чтение и запись TXT, валидация, множители и единые цены игры наоборот, обнаружение внешних правок |

| Form1 / BigGameControl | Операторские команды, поля-черновики, доступность кнопок и общие сервисы |
| AppearanceSettings / BankEditor | Редактирование отдельного черновика с явным сохранением; подготовка не меняет матч |
| Tablo / BigGameTablo | Отображение готового состояния без начислений, файловой записи и звуков |

| DisplayScaleWarning | Проверка масштаба каждого монитора при запуске и необязательная рекомендация 100% |
| OperatorUi / OperatorWindows | Общая компоновка, диалоги, метка черновика и размещение операторских окон на основном мониторе |

Пульты собираются программно: BuildUi вызывает функции отдельных функциональных групп. Зрительские формы сохраняют геометрию WinForms Designer. Option Strict On включён для всего проекта.

### Границы игрового состояния

Обработчик передаёт команду в GameSession. Сначала изменяется независимая копия и проверяются ограничения. Только успешная команда становится текущим состоянием и попадает в историю. Наружу сессия также возвращает копию: пульт или табло не могут незаметно изменить историю через общий массив.

Копирование в памяти выполняется непосредственно по полям и вложенным объектам. XML используется для диска, а не для каждого запроса состояния. Отмена восстанавливает снимок обоих режимов; не выполняет обратную арифметику и не проигрывает звук повторно. Рендер не начисляет очки, поэтому повторное открытие окна безопасно.

В большой игре Tab проходит поля в порядке «ответ → очки → следующий ответ», включая переход между участниками. При входе в очки через Tab или Shift+Tab всё число выделяется для замены новым вводом.

Поля ответа остаются черновиками до явной команды. Настройки оформления, запись TXT, таймер, показ окна и допуск Buzz! не входят в игровую Undo. Применение оформления не меняет счёт, раскрытия, маску, текущую заставку и ход таймера. Подложка масштабируется один раз на размер холста; созданные Bitmap и Font освобождает их владелец.

Задержка начала мигания лампы Buzz! задаётся в «Настройки → Экран и звук», по умолчанию 250 мс; 0 отключает задержку. Значение сохраняется в config.xml (BuzzLampDelayMilliseconds); прежние профили без поля получают 250 мс. Смена оформления сохраняет задержку как параметр оборудования. Применение действует со следующего победителя, не задерживает арбитраж и запуск звука; длительность мигания остаётся 15 секунд после задержки.

BuzzReceiver использует HidLibrary для поиска и открытия устройства, а обмен выполняет через OverlappedIo. Таймаут ожидания не завершает запрос Windows: перед освобождением буфера и OVERLAPPED вызываются CancelIoEx и GetOverlappedResult. Устройство закрывает только владеющий им USB-worker после завершения обмена. Ошибка устройства переводит приёмник в состояние ошибки; отсутствие новых отчётов само по себе не означает отключения.

## Данные и восстановление

Рабочий каталог — `%LOCALAPPDATA%/StoKOdnomuControl`. Для изолированного запуска он переопределяется переменной STOKODNOMU_DATA_DIR. Приложение допускает один экземпляр для пользователя.

| Файл | Назначение |
|---|---|
| game.xml | Матч и до 100 снимков Undo; формат 2, поддерживается преобразование формата 1 |
| game.xml.bak | Предыдущий целый снимок матча |
| archive/match-…/ | Копии прежних game.xml и game.xml.bak перед явным новым матчем; COMPLETE.txt отмечает завершённое копирование |
| actions.log | Вспомогательный журнал; не является источником восстановления |
| appearance/config.xml | Выбранный профиль, параметры экрана и звука; формат 1 |
| appearance/config.xml.bak | Предыдущая версия профиля |
| appearance/media/ | Копии изображений, на которые ссылаются профили |
| выбранный TXT и TXT.bak | Подготовленная база и её предыдущая записанная версия |

Если при запуске найдены game.xml или game.xml.bak, сначала требуется выбрать восстановление либо новый матч. «Отмена» оставляет сохранения нетронутыми и блокирует игровые команды до решения. Перед новым матчем оба имеющихся файла копируются в отдельный каталог archive/match-…/ и проверяются по SHA-256. Ошибка архивирования отменяет начало нового матча; частичная копия не получает COMPLETE.txt. Архивы не участвуют во вращении .bak и автоматически не удаляются. Для ручного восстановления закройте приложение и скопируйте нужный XML из завершённого архива обратно в рабочий каталог, предварительно сохранив его текущие файлы.

Запись сначала заканчивается во временном файле, затем публикуется атомарной заменой. Временные .tmp после аварий не считаются сохранениями и не загружаются. При ошибке диска игровое действие остаётся в памяти; оператор получает сообщение, что автосохранение не удалось. Следующая успешная запись включает текущее состояние. Отказ журнала сообщается отдельно: уже сохранённый матч от него не теряется.

Меню «Матч и сбросы… → Восстановить игру…» читает основной XML, «Восстановить резервную копию…» — game.xml.bak. Оба варианта сначала проверяют наличие обязательных элементов в самом XML, затем данные матча и всей истории. Пустой корень, пропуски, дубли обязательных элементов и пустые ссылки отклоняются; формат 1 проверяется с учётом его прежней структуры. Ошибка не заменяет текущий матч или черновики. После восстановления таймер и допуск Buzz! остановлены. Незавершённый отсчёт и неопубликованные поля не восстанавливаются.

Первая запись после восстановления .bak сохраняет повреждённый основной файл как game.xml.rejected-..., не затирая хороший резерв. Следующие записи снова используют обычную .bak. Для восстановления оформления можно открыть config.xml.bak через «Открыть профиль…» и применить его; повреждённый текущий конфиг также сохраняется отдельно. При нерабочем оформлении на старте доступен встроенный вариант «Тупикон 2026» с сообщением об ошибке.

Резервную базу можно открыть в редакторе и сохранить под новым именем. Запись TXT не откатывается игровой отменой. При внешнем изменении открытого TXT редактор предлагает перечитать его либо сохранить свой черновик под другим именем.

## Оформление и ресурсы

В папке lib/profiles рядом с EXE каждый профиль занимает отдельный каталог с произвольным именем, config.xml и изображениями. Пример структуры в исходниках: `profiles/tupikon-2025/config.xml`. Список также читает profiles из пользовательского каталога. Комплектные оформления: «Тупикон 2025» с белым текстом и «Тупикон 2026» с чёрным.

Выбор из списка и «Открыть профиль…» заменяют черновик только после проверки выбранного файла и согласия отбросить несохранённые правки. При отказе или ошибке сохраняются прежние поля и выбранный пункт; успешное применение не вызывает повторного подтверждения.

XML содержит имя, цвет #RRGGBB, относительные пути и настройки основной/большой игры. Четыре основных раунда наследуют общий стиль либо имеют собственный. Большая игра независима. При импорте проверяются картинки и пути; выход за папку и ссылки внутри медиа отклоняются. Старые profile.xml и числовой TextArgb остаются совместимыми.

Изображения копируются побайтно без изменения оригиналов и перекодирования JPEG в PNG. Имя в media определяется SHA-256 содержимого, поэтому переключение уже известных оформлений не создаёт новых копий. Старые относительные пути и папки media прежнего формата читаются. Резервные конфиги сохраняют свои картинки; автоматическое удаление архивных медиа не выполняется.

Двадцать три общих ресурса перечислены в My Project/Resources.resx: изображения 2026 года, 16 WAV и графика пасхалки. Они используются кодом. Оформление 2026 встроено как резерв при ошибках внешнего профиля; отдельные копии в profiles позволяют выбирать и переносить его обычным способом.

Новый дизигн содержит художественные варианты, два используемых шрифта в static и их OFL.txt; из Новые звуки ещё встраиваются пять ff_reveal. Корневой XCF и PNG — художественные исходники. Эти папки не нужны рядом с готовым EXE, но не являются целиком неиспользуемыми материалами проекта. JetBrains Mono Regular/Bold поставляются с OFL; установки семейства в Windows не требуется.

## Формат базы и начисление

TXT содержит 24 непустые строки UTF-8: 18 пар Ответ&число для простой, двойной и тройной игры и шесть текстов игры наоборот. Чтение допускает BOM и CRLF/LF; запись — UTF-8 без BOM, CRLF. Ответы обязательны, до 120 символов; исходное число — целое 0…999. Сумма раунда не ограничивается 100.

Число на табло остаётся исходным, начисление в банк умножается на 1/2/3. Цены наоборот: 15, 30, 45, 60, 120, 240. Скрытие и повторный показ не начисляют ответ второй раз. Правка уже начисленной цены меняет банк на разницу; после передачи банка сначала отменяется передача. Общий итог большой игры складывается из открытых цен и отдельной ручной поправки.

## Оборудование

Приёмник Buzz! имеет VID 054C, PID 1000. Красные кнопки — HID usages 1, 6, 11, 16. Чтение и лампы относятся к одному устройству; сопоставление соответствует [драйверу Sony](https://github.com/torvalds/linux/blob/master/drivers/hid/hid-sony.c), разбор дескриптора выполняется [HidP_GetUsages](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidpi/nf-hidpi-hidp_getusages).

Без приёмника обычная игра работает, аппаратные команды блокируются. Первое нажатие закрывает допуск; ничья в одном отчёте требует переигровки. При отключении/подключении USB допуск не восстанавливается автоматически. Таймер 20/25 секунд использует Stopwatch, а не длину трека; эффекты, Buzz! и отсчёт имеют независимые каналы.

Настоящий приёмник, лампы, слышимая синхронизация, проектор и масштаб Windows проверяются на оборудовании. Программные имитации и DrawToBitmap не подтверждают задержки радиоканала или качество вывода на конкретный проектор.

## Размещение файлов

ApplicationFiles задаёт пути lib/Fonts, lib/profiles и lib/bases относительно AppDomain.BaseDirectory. Файловый диалог загрузки базы открывается в lib/bases. Пользовательский каталог профилей и сохранений не переносится: он остаётся в %LOCALAPPDATA%/StoKOdnomuControl.

Компилируемый app.config содержит `probing privatePath="lib"`: CLR находит управляемые зависимости до входа в код приложения. Поэтому `StoKOdnomuControl.exe.config` остаётся рядом с EXE. Порядок поиска описан в [документации .NET Framework](https://learn.microsoft.com/en-us/dotnet/framework/configure-apps/file-schema/runtime/probing-element). Собственного AssemblyResolve и изменения текущей папки для загрузки DLL нет.

MSBuild копирует зависимости в lib, контент — в соответствующие подпапки lib. Упаковка добавляет документацию в lib/docs, лицензии компонентов в lib/licenses и манифест в lib/PACKAGE_MANIFEST.txt. Неизменённые исходные базы и художественные материалы остаются на своих местах в репозитории.
